Small Domain-Specific Languages as Interfaces for LLM-Assisted Development

A case study in structured musical representation, validation and browser-based notation

Jamie Gabriel · SAJA Music · November 2026 · Technical research note

Abstract

Large language models (LLMs) provide flexible mechanisms for translating human intentions into software artefacts, but natural-language interaction introduces ambiguity when the underlying task is structurally constrained. This paper presents a small domain-specific language (DSL) developed to represent short beginner piano compositions and facilitate their transformation into interactive browser-based scores. The system combines a graphical piano-roll editor, a compact pitch-duration notation, and an existing VexFlow rendering environment. Drawing on concepts from compiler construction, domain-specific language design and human–computer interaction, the paper distinguishes syntactic validity, musical semantic constraints and graphical presentation. It argues that compact intermediate representations can reduce unnecessary interpretation in LLM-assisted workflows while enabling deterministic validation. The case study is presented as a design analysis rather than a controlled evaluation: improved reliability is a plausible architectural benefit, not an empirically established outcome. Implications for educational software, computational musicology and hybrid deterministic–generative systems are discussed.

1. Introduction

Generative programming tools are frequently used through conversational descriptions of desired behaviour. This interaction is valuable for open-ended design, yet it is less appropriate when an author has already specified the underlying data and seeks faithful transformation rather than reinterpretation. A musical score provides a useful example: pitch, onset, duration, voice assignment and notation are related but distinct dimensions of a structured object.

This paper examines a practical implementation developed within SAJA Music, a collection of freely accessible music-education resources. The immediate requirement was to author short piano pieces for beginner students, often using fixed five-finger positions, and render them as interactive scores. The underlying notation engine uses VexFlow, a JavaScript library supporting SVG and Canvas engraving (VexFlow, n.d.). Rather than repeatedly describing note-level changes in natural language, a browser-based piano roll was developed to export a concise textual score representation.

The principal argument is that a small formal interface can be more useful than increasingly elaborate prompting for tasks whose variable inputs are already well understood. This is consistent with the established rationale for DSLs: constrain expressive scope in order to make domain intentions explicit (Fowler, 2010).

2. Conceptual background

2.1 Domain-specific languages and abstraction

A DSL is a language designed around a restricted class of problems rather than general-purpose computation (Fowler, 2010). Its value depends on selecting abstractions that expose meaningful domain operations without reproducing an entire software system. For short beginner compositions, a full score-interchange format can encode considerably more information than the task requires. In the present application, clefs, layout conventions and most engraving decisions are already fixed; the principal variables are pitch, duration and hand assignment.

2.2 Direct manipulation and representational distance

A piano roll enables musical events to be entered spatially, with pitch represented vertically and time horizontally. This design can be interpreted through the account of direct manipulation offered by Hutchins, Hollan and Norman (1985): interfaces can reduce the distance between users’ intentions and the operations available to them. Here, the user need not learn a textual grammar because the interface generates the notation automatically. The resulting text remains inspectable and portable.

2.3 Intermediate representations and LLM-mediated transformation

Compiler architectures separate parsing, semantic analysis and code generation through intermediate representations. The same separation is useful in LLM-assisted development, although the analogy must not be overstated. A conventional compiler implements defined transformations; an LLM generates probabilistic outputs and cannot be assumed to preserve semantics. An explicit intermediate representation can narrow the transformation task and make discrepancies easier to detect, but it does not by itself guarantee correctness.

3. Case study and system design

3.1 Authoring context

The application supports the creation of short original piano pieces for beginning students, including a collection titled Times of Day. Pieces are entered into a standalone HTML piano roll, auditioned locally and exported as text. A separate score-rendering environment applies established VexFlow engraving conventions, including optional note names inside noteheads, fingering and interactive playback.

3.2 Data flow

The design separates five responsibilities: graphical input, serialisation, parsing, semantic validation and rendering. In the current workflow an LLM may mediate the transformation from the serialised score into the existing rendering implementation.

Conceptual pipeline

Piano roll → Textual DSL → Parser / validated musical model → LLM-assisted implementation → VexFlow score

In a more mature implementation, the parser and rendering adapter could operate deterministically, leaving the LLM to support code maintenance, exercise generation or pedagogical variations.

4. A minimal musical DSL

The format expresses each event as a pitch-duration pair. Measure boundaries are marked by vertical bars, and right- and left-hand material are distinguished explicitly.

Time: 4/4
Tempo: 80 bpm
RH: C4-quarter C4-quarter D4-quarter D4-quarter |
    E4-quarter F4-quarter D4-quarter C4-quarter |
    C4-whole
LH: C3-whole |
    D3-quarter D3-quarter D3-quarter E3-quarter |
    C3-whole

A simplified grammar can be stated in extended Backus–Naur form (EBNF):

score      = time, tempo, right_hand, left_hand ;
time       = "Time:", integer, "/", integer ;
tempo      = "Tempo:", integer, "bpm" ;
right_hand = "RH:", sequence ;
left_hand  = "LH:", sequence ;
sequence   = measure, { "|", measure } ;
measure    = note, { note } ;
note       = pitch, "-", duration ;
pitch      = note_name, octave ;
note_name  = "A" | "B" | "C" | "D" | "E" | "F" | "G" ;
octave     = digit ;
duration   = "whole" | "half" | "quarter" ;

This illustrative grammar deliberately omits accidentals, rests, ties, tuplets and polyphonic voices. It also abstracts away whitespace and lexical rules. These omissions are acceptable only within the constrained repertoire; they are not properties of music notation generally. A production grammar would need explicit tokenisation rules and support for any additional rhythmic or pitch vocabulary used by the authoring interface.

5. Parsing and semantic validation

Parsing establishes whether an input conforms to a grammar; semantic validation establishes whether the parsed structure satisfies musical constraints. The sequence C4-quarter D4-quarter E4-quarter is syntactically plausible but occupies only three quarter-note beats. In a complete 4/4 bar it is therefore invalid unless an incomplete measure is explicitly permitted.

const durations = { whole: 4, half: 2, quarter: 1 };
function validateMeasure(notes, expectedBeats = 4) {
  const total = notes.reduce(
    (sum, note) => sum + durations[note.duration], 0
  );
  return total === expectedBeats;
}

For this restricted vocabulary, integer beat counts are sufficient. General rhythmic notation requires rational duration arithmetic, with expected bar length derived from the time signature. Other checks include pitch-range restrictions, consistent measure counts between hands, recognised durations and well-formed pitch tokens. These checks are deterministic and should not depend on model judgement.

A practical validation pipeline would parse tokens into typed events, check invariants, produce diagnostics tied to bar and hand, and compare rendered or generated output against the source event sequence. This is a proposed extension; no formal error-rate benchmark is reported here.

6. The role of the LLM

LLM use is most defensible where flexible transformation is beneficial and where its output can be checked independently. Given a validated score representation, a model may generate VexFlow code, MusicXML, MIDI conversion routines, a transposed exercise or a different pedagogical presentation. The source representation need not change across these targets.

However, output variability remains a significant limitation. The model may omit a note, alter a duration or introduce an inconsistent API call. Consequently, generated artefacts should be treated as untrusted transformations pending validation. This distinction is essential: the architectural proposal is not that LLMs replace parsers, but that parsers reduce the amount of interpretation demanded of LLMs.

7. Discussion

7.1 Scope as a design advantage

Restricting the DSL to a narrow pedagogical use case makes the language easy to inspect and the editor straightforward to maintain. A more expressive notation system may eventually be required, but premature generalisation would increase complexity without necessarily improving the current authoring workflow.

7.2 Implications beyond notation

The same pattern could support graphical mathematical-exercise builders, structured data-analysis pipelines or timeline editors. In each case, a domain interface captures the user's intentions, a compact representation makes those intentions explicit, and a validated transformation produces an output artefact. This is a design proposition rather than a claim of demonstrated generalisability.

7.3 Limitations and future evaluation

This paper describes one implementation context and does not present a comparative user study. Claims about reduced ambiguity or improved reliability should therefore be evaluated empirically. A useful study could compare natural-language-only prompting with DSL-mediated prompting on matched score-editing tasks, measuring event-preservation accuracy, time to completion, corrective prompts and user workload. Further development should include round-trip parsing and serialisation tests, structured error reporting and a deterministic VexFlow adapter.

8. Conclusion

The case study illustrates how a compact DSL can formalise musical intentions at the boundary between a human author, a graphical interface and a generative programming system. Separating source events from engraving conventions clarifies responsibilities and enables independent validation. The broader contribution is an architectural argument: when a task is highly structured, reliable LLM-assisted development may depend as much on careful representation design as on the quality of the prompt or the capabilities of the model. In this instance, a small parser and a deliberately limited musical language are sufficient to make the composition-to-score workflow more explicit and maintainable.
